## Wave 1: Environment & Core Model Hierarchy

**Primary Goal:** Transition from a monolithic `if/else` class to a clean, inheritance-based Class hierarchy while establishing a professional development environment.

* **Task Description:** 1.  Initialize a repository with `src/` and `tests/` folders.
2.  Configure `pyproject.toml` (using setuptools) with `tensorflow`, `numpy`, and `typing` dependencies. Create `requirements-dev.txt` for `pytest`, `black`, and `mypy`.
3.  Create `src/models/base.py` defining an abstract class `BaseSpinSystem(tf.Module)`. It must define the interface for `compute_energy()`, `initialize_state()`, and `validate_shapes()`.
4.  Implement concrete subclasses: `IsingSystem`, `SphericalSystem`, and `Z2GaugeSystem`.
5.  Move model-specific logic (like `_apply_spherical_constraint` or `compute_plaquette`) into the respective concrete classes.
* **Acceptance Criteria:**
* `IsingSystem` can be instantiated without mentioning "spherical" or "z2" in its logic.
* The `Z2GaugeSystem` maintains the specific link-lattice shape `(replicas, L, L, 2)`.
* Code passes a basic `pytest` that checks if `compute_energy()` returns a tensor of shape `(replicas,)`.


* **Definition of Done:**
* Environment is active and `pip install -e .` works.
* No `if model == "ising"` branches exist in the code.
* Linter (Black) passes with zero errors.

## Wave 2: Decoupled Measurement Suite

**Primary Goal:** Create a system where measurements are "Observers" that take a Spin System as an argument, making it easy to add new observables without touching the core model code.

* **Task Description:**
1. Create `src/measurements/base.py` with an abstract `Measurement` class.
2. Implement `ScalarMeasurements` (Energy, Magnetization, Susceptibility) in `scalars.py`.
3. Implement `CorrelationMeasurements` (Overlap Matrix) in `correlations.py`.
4. Implement `GaugeMeasurements` (Wilson Loops, Plaquette values) in `gauge.py`.
5. Each measurement class constructor must accept an instance of `BaseSpinSystem`.


* **Acceptance Criteria:**
* A user can run `Magnetization(my_system).compute()` and get the same numerical result as the legacy code.
* `WilsonLoop` measurement raises a `TypeError` or `ValueError` if passed an `IsingSystem`.


* **Definition of Done:**
* All measurement logic is removed from `models/`.
* Test suite contains "cross-check" tests comparing the modular output against the `legacy_core.py` outputs for the same random seed.

## Wave 3: MCMC Dynamics & Dispatcher

**Primary Goal:** Implement the Metropolis-Hastings update logic as a separate "Driver" that modifies the state of a system.

* **Task Description:**
1. Create `src/dynamics/base.py` defining how a dynamic method should interact with a system (e.g., `step()` and `sweep()`).
2. Implement `MetropolisDynamics(BaseDynamics)` in `dynamics/metropolis.py`.
3. Move the "disturbance" logic (spin flips and rotations) into this class. The `MetropolisDynamics` class should be agnostic of the model type but still figure out which method to use based on the model type. Ising models use spin flips, while spherical models use rotations.
4. Implement a `SweepManager` that handles the `while_loop` for MCMC, measurement granularity, and `TensorArray` tracking. The tracking should be optional and only enabled when the `tracker` argument is provided. The tracker should be a class. If no tracker is added the loop should only update the model without tracking.
5. There should be a testing suite that tests the `MetropolisDynamics` class on all models created in Wave 1. 
6. There should also be a testing suite to test the `SweepManager` class on all models created in Wave 1.
7. Implement a testing suite for the cross-checks between the old and new code. Run the simulation for a few steps and compare the results.

* **Acceptance Criteria:**
* The `MetropolisDynamics` class can perform a sweep on any of the models created in Wave 1.
* The dynamics class successfully updates the `tf.Variable` state inside the `SpinSystem` object.
* The cross-checks between the old and new code are successful.
* The `SweepManager` class successfully tracks the observables for a few steps with a given granularity.
* The `SweepManager` class successfully runs a simulation for a few steps without tracking.

* **Definition of Done:**
* A script can run a 1000-step Metropolis sweep on an `IsingSystem` and return a dictionary of tracked observables.
* All methods are decorated with `@tf.function` and run without retracing warnings.

## Wave 4: Stochastic Dynamics (Langevin) & Multi-Temp API

**Primary Goal:** Extend the dynamics to support Gradient-based methods and provide a high-level API for large-scale simulations.

* **Task Description:**
1. Implement `LangevinDynamics(BaseDynamics)` in `dynamics/stochastic.py`.
2. Use `tf.GradientTape` within the Langevin step to calculate the force  based on the system's `compute_energy()` method.
3. Ensure `SphericalSystem` constraints are re-applied after the Langevin update.
4. Implement `MultiTemperatureRunner` in a new `simulations/` folder to orchestrate the `multi_temperature_sweep` logic.


* **Acceptance Criteria:**
* `LangevinDynamics` works for `SphericalSystem` (continuous spins).
* `MultiTemperatureRunner` can run simulations in parallel or sequence across a provided list of `betas`.


* **Definition of Done:**
* Full documentation of the new API.
* Final testing suite passes with >90% code coverage.
* The repo includes a `examples/comparison.py` script showing a system evolving via Metropolis vs. Langevin.
